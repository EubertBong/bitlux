# Deploying Bitlux CRM

| Layer    | Service                    | Plan | Config in repo                         |
|----------|----------------------------|------|----------------------------------------|
| Backend  | Render (Docker web service) | Free | `render.yaml`, `backend/Dockerfile`    |
| Frontend | Cloudflare Pages            | Free | `frontend/public/_headers`, `_redirects`, build guard in `vite.config.ts` |
| Database | Neon (PostgreSQL 16)        | Free | `make *-prod` targets, `.github/workflows/partition-maintenance.yml` |

Total cost: $0. Nothing in this document deploys anything by itself; every step
that touches a provider is done by you, in the order below.

## The one thing to get right: two database roles

The schema relies on row-level security for tenant isolation (DATA_MODEL.md 1.7).
RLS does **not** bind superusers or any role with `BYPASSRLS`, and Neon's
console-created roles are members of `neon_superuser`, which has `BYPASSRLS`. So:

| Role                       | Used by                                      | Env var            |
|----------------------------|----------------------------------------------|--------------------|
| Neon owner role (yours)    | `alembic`, seed, partition maintenance, CI   | `DATABASE_URL`     |
| `bitlux_app` (`NOBYPASSRLS`, `LOGIN`) | the API on Render                  | `APP_DATABASE_URL` |

`make app-role-prod` creates `bitlux_app`. The API **refuses to start** if
`APP_DATABASE_URL` connects as a role that bypasses RLS, and `make db-check-prod`
tells you which kind of role a URL is. Never give Render the owner URL.

## Prerequisites

- A Neon project on PostgreSQL 16 with a database named `bitlux_crm` (create it in
  the Neon console; the default `neondb` works too if you keep it in every URL).
  Pick the Neon region closest to the Render region you will choose (Render free
  offers Oregon, Ohio, Virginia, Frankfurt, Singapore).
- The owner connection string from the Neon console, in the form
  `postgresql://<user>:<pw>@<endpoint>.neon.tech/bitlux_crm?sslmode=require`.
  A trailing `&channel_binding=require` is fine; the app and scripts strip it.
- Render and Cloudflare accounts linked to the GitHub account that owns this repo.
- Locally: `make venv` has been run (the `*-prod` targets use `backend/.venv`), `psql` is
  installed (`make db-check-prod` uses it),
  and the code is pushed to GitHub (`master`).

## Step 0. Prepare the database (from your machine)

```bash
export DATABASE_URL='postgresql://<owner>:<pw>@<endpoint>.neon.tech/bitlux_crm?sslmode=require'

make db-check-prod              # SELECT 1: OK ... bitlux_app: MISSING
export APP_DB_PASSWORD="$(python3 -c 'import secrets; print(secrets.token_urlsafe(24))')"
make app-role-prod              # creates bitlux_app + grants your owner membership; PRINTS the APP_DATABASE_URL -- copy it
make migrate-prod               # alembic upgrade head (001 .. 017)
make partition-maintenance-prod # 12 months of audit_logs partitions
make seed-prod                  # optional demo tenant; 5-second Ctrl-C window
make db-check-prod              # bitlux_app: exists, login=true, bypassrls=false; alembic head: 017
```

Every `*-prod` target refuses to run if `DATABASE_URL` is unset or points at
localhost, and echoes the target with the password redacted before it acts.

`make app-role-prod` also runs `GRANT bitlux_app TO CURRENT_USER`. The seed and
verify scripts write tenant data via `SET LOCAL ROLE bitlux_app` so RLS is actually
exercised; a real superuser may switch to any role, which is why the local stack
never needed this, but the Neon owner is not a superuser and PostgreSQL only allows
`SET ROLE` into roles you are a member of. Skip the target and `make seed-prod`
fails with `permission denied to set role "bitlux_app"`; the fix is the target, or
`GRANT bitlux_app TO CURRENT_USER;` as the owner. Re-running it is safe.

## Step 1. Backend on Render

1. Render dashboard → **New → Blueprint** → select the repo → Render reads
   `render.yaml` and proposes the `bitlux-api` web service (Docker, free plan,
   health check `/health`). Apply.
2. It will stop and ask for the two `sync: false` variables:
   - `APP_DATABASE_URL` = the URL printed by `make app-role-prod`
     (`postgresql+asyncpg://bitlux_app:<pw>@<endpoint>.neon.tech/bitlux_crm?sslmode=require`)
   - `CORS_ORIGINS` = `["https://bitlux-crm.pages.dev"]` for now; you will correct
     it in Step 3 once Cloudflare tells you the real project URL.
   `JWT_SECRET`, `JWT_REFRESH_SECRET` and `FIELD_ENCRYPTION_KEY` are generated by
   Render and persist for the life of the service. `APP_ENV=production`,
   `REFRESH_COOKIE_SAMESITE=none`, `REFRESH_COOKIE_SECURE=true` come from the file.
3. Deploy. The first Docker build takes a few minutes. Then:
   ```bash
   curl -s https://bitlux-api.onrender.com/health      # {"status":"ok","db":"ok"}
   ```
   The service log should contain `database role 'bitlux_app': RLS enforced`.
   If the name `bitlux-api` is already taken on Render, the hostname gets a suffix;
   use whatever the dashboard shows from here on.

## Step 2. Frontend on Cloudflare Pages

4. Cloudflare dashboard → **Workers & Pages → Create → Pages → Connect to Git** →
   select the repo, production branch `master`.
5. Build configuration:
   - Framework preset: **Vite**
   - Build command: `npm run build`
   - Build output directory: `dist`
   - Root directory: `frontend`
6. Environment variables (set for **Production and Preview**):
   - `VITE_API_BASE_URL` = `https://bitlux-api.onrender.com/api/v1`
   - `NODE_VERSION` = `22`
   The build fails immediately with a clear message if `VITE_API_BASE_URL` is unset.
7. **Save and Deploy**. Copy the project URL, e.g. `https://bitlux-crm.pages.dev`.

## Step 3. Wire CORS back to Render

8. Render → `bitlux-api` → Environment → set `CORS_ORIGINS` to the exact Pages
   origin, no trailing slash, e.g. `["https://bitlux-crm.pages.dev"]`. To allow
   preview deployments as well, list them: `["https://bitlux-crm.pages.dev","https://<hash>.bitlux-crm.pages.dev"]`.
9. Save. Render restarts the service on an environment change (redeploy manually
   if it does not).

## Step 4. Verify end to end

10. Open the Pages URL. Sign in as `owner@demo.test` / `Demo!2026` (also
    `broker@demo.test`, `ops@demo.test`, same password) — these exist only if you
    ran `make seed-prod`.
11. Check: the dashboard loads; **Clients** lists Demo Brokerage; ⌘K / Ctrl-K
    search for `gulf` returns Gulfstream aircraft and models; the client's
    **Relationship** tab renders the graph.
12. DevTools → Application → Cookies → `https://bitlux-api.onrender.com`:
    `bitlux_refresh` with **HttpOnly ✓, Secure ✓, SameSite=None, Path=/api/v1/auth**.
    Local Storage for the Pages origin holds only `bitlux-theme` and `bitlux-session`
    (a boolean); no tokens.
13. From a terminal:
    ```bash
    curl -si -X OPTIONS https://bitlux-api.onrender.com/api/v1/auth/login \
      -H 'Origin: https://bitlux-crm.pages.dev' -H 'Access-Control-Request-Method: POST' | grep -i access-control
    ```
    must show `access-control-allow-origin: https://bitlux-crm.pages.dev` and
    `access-control-allow-credentials: true`.

## Step 5. After go-live

- **GitHub secret** `PROD_DATABASE_URL` = the Neon **owner** URL. The workflow
  `.github/workflows/partition-maintenance.yml` runs on the 1st of each month at
  03:00 UTC; run it once by hand (Actions → Monthly partition maintenance → Run
  workflow) to confirm the secret works.
- **Uptime monitor**: Render free spins the service down after 15 minutes idle and
  the first request then takes up to a minute. A free monitor (UptimeRobot,
  cron-job.org) hitting `/health` every 10 minutes keeps it warm; the free plan's
  750 instance-hours a month cover one always-on service.
- **Neon autosuspend**: the free compute suspends after 5 minutes idle; the first
  query afterwards takes about a second. Harmless; `/health` may report 503 for
  that one request, which Render tolerates.
- **Secrets**: rotating the JWT secrets logs everyone out (intended).
  `FIELD_ENCRYPTION_KEY` must never change without re-encrypting the `[enc]`
  columns; do not "reset" it in the Render dashboard.

## Troubleshooting

- **API log: `refusing to start: database role ... bypasses row-level security`** —
  `APP_DATABASE_URL` is the owner URL. Use the `bitlux_app` URL from `make app-role-prod`.
- **API log: `APP_DATABASE_URL is not set`** — the variable is missing or named
  `DATABASE_URL`; the runtime deliberately reads only `APP_DATABASE_URL`.
- **API log: `these are still dev defaults`** — a generated secret is missing; check
  the three `generateValue` entries exist in the service's environment.
- **`/health` returns 503** — the database is unreachable from Render: wrong
  password, wrong endpoint, or Neon suspended (transient). `make db-check-prod`
  with the same URL (owner or app) reproduces it from your machine.
- **Cold start** — see Step 5.
- **Cookie not set / logged out after 15 minutes** — confirm
  `REFRESH_COOKIE_SAMESITE=none`, `REFRESH_COOKIE_SECURE=true`, `CORS_ORIGINS` is the
  exact Pages origin without a trailing slash (the API strips one if present), and
  the login response carries `Set-Cookie: bitlux_refresh=...; SameSite=none; Secure`.
  FastAPI is configured with `allow_credentials=True`. Note that `*.pages.dev` and
  `*.onrender.com` are different sites, so this is a third-party cookie: Safari and
  browsers with third-party cookies disabled will drop it (login works, the silent
  refresh 15 minutes later does not). The durable fix is custom domains on one
  site, e.g. `app.example.com` + `api.example.com`, after which
  `REFRESH_COOKIE_SAMESITE` can go back to `lax`.
- **CORS preflight fails** — Network tab, the `OPTIONS` request: a 400 means the
  `Origin` header does not match any entry in `CORS_ORIGINS`.
- **Neon extensions** — migration 001 creates `citext` and `ltree`; both are
  available on Neon. If 001 fails anyway, run `CREATE EXTENSION IF NOT EXISTS citext;`
  and `... ltree;` as the owner and re-run `make migrate-prod`.
- **`sslmode` / `channel_binding` errors** — the API translates `?sslmode=` into
  asyncpg's `ssl=` argument and drops `channel_binding`; alembic strips `sslmode`
  (TLS is still negotiated). If you see `unexpected keyword argument 'sslmode'`,
  the URL bypassed `app.config.asyncpg_engine_args` — report it.
- **Cloudflare Pages 404 on a deep link** — confirm `_redirects` is in the deployed
  output (`dist/_redirects`); Pages also falls back to `index.html` automatically
  when the project has no `404.html`.
- **Cloudflare build fails with `VITE_API_BASE_URL is required`** — set it under
  Settings → Environment variables for the environment that failed (Production and
  Preview are separate).

## Rollback

- Backend: Render → Deploys → **Rollback** to the previous image (env vars are not
  part of a deploy). Migrations are forward-only in production; `make downgrade`
  exists for local use.
- Frontend: Cloudflare Pages → Deployments → **Rollback** on any earlier build.
